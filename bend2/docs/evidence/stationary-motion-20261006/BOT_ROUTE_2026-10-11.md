# Bot result consumed by the application

The earlier real bot journey observed Worker targets and a completed move, but
could not distinguish a Worker result from the application's serial fallback.
The browser executor now attaches a small `botExecution` diagnostic to the frame
that applies a bot choice: actual route, generation, requested/applied revision
and choice ID. Later and refinement frames receive null. Bend still validates and
applies the choice; scheduling, fallback behavior, rules and proofs are unchanged.
The tag adapter changes only its exact worker preimage digest.

One real portrait journey used installed Chrome on Windows, a 400x800 viewport
and the application's 512x1024 canvas. It started human White / bot Black through
the painted controls, selected the visibly reviewed g1 knight neck, played e2-e4,
and waited for the bot reply. The frame reported Worker route, generation 1,
revision 1 to 2 and choice 20065 (g8-f6). Frame 20's revision was 2; the stored
command had expected revision 1 and action 20065. The two real bot Worker targets
provide complementary hosting evidence. Same-context offline reload preserved
both commands and displayed revision 2; the cached build bytes matched.
There were no page, console, request or Worker faults.

The new package reuses unchanged Scene/Controller/Menu emissions, bot library,
helper, assets and transport. No compiler execution or new unit/integration test
ran. The existing bounded application runner was used for this journey, without
synthetic packets, mocked hosts, forced policy or a scenario matrix. The original
Node and Chrome processes, streams, loopback server and nonkill Job closed normally.
Earlier build/runner failures remain private historical evidence with known closure.
